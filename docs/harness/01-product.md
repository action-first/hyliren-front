# Product & Domain

## 한 줄 정의

성형 고민 매칭 + 의사결정 지원 + 실행 서비스 플랫폼

## 핵심 흐름

```
[콘텐츠로 유입] → 고민 등록 → 병원 제안서 → 비교 → 검증 리포트 → 직접 예약 → 부가 서비스
```

## Identity 분리 (핵심 가드레일)

| | User (수요측) | Member (공급측) |
|---|--------------|----------------|
| 누구 | 고객, 레퍼러 | 병원, 관리자 |
| 앱 | FO | PO, BO |
| 테이블 | 별도 | 별도 |
| 온보딩 | 별도 | 별도 |

## 수익 모델

| 누가 | 뭘 | 언제 |
|------|-----|------|
| Member(병원) | CRM 구독료 | 가입 시 |
| Member(병원) | 제안서 크레딧 | 발송 시 |
| Member(병원) | 광고/노출비 | 상시 |
| User(고객) | 검증 리포트 (5~20만) | 비교 단계 |
| User(고객) | 실행 서비스 | 방문 준비 |
| User(고객) | VIP 패키지 | 방문 준비 |

## 핵심 엔티티 (5개만 — 절대 늘리지 않음)

```
User     — 수요측 (buyer + referrer)
Member   — 공급측 (partner + admin)
Concern  — 고민 (매칭의 입력)
Proposal — 제안서 (매칭의 출력)
Order    — 주문 (ReportOrder / ServiceOrder — 모든 결제의 단위)
```

나머지는 전부 이 5개의 확장(extension)이다.
새 core entity를 추가하려면 강한 이유가 필요하다.

## 매칭 채널 (유일한 경로)

```
User → Concern(입력) → Proposal(출력) ← Member
```

금지:
- 다이렉트 메시징이 주 흐름이 되는 것
- 제안서 없이 직접 예약
- 자유형 병원 연락

## 상태 기반 시스템 (UI가 아닌 엔티티 상태가 흐름을 결정)

Concern.status가 모든 것을 결정한다:
- `submitted` → 병원이 제안서 발송 가능
- `proposal_received` → 고객이 비교 가능
- `comparing` → 리포트 구매 가능
- `hospital_selected` → 서비스 구매 가능

UI는 상태를 보여주기만 한다. UI 안에서 if/else로 흐름 제어 금지.

## 콘텐츠 엔진

FO에 성형/피부 아티클 매일 1~2개 자동 발행.
블로그가 아니라 "SEO 유입 → 고민 등록 전환" 퍼널 진입 장치.
Article은 first-class 도메인이며, 반드시 Concern 생성으로 연결.

### 카테고리
- 시술/수술 설명 | Before/After 케이스 | 비용/가격 가이드
- 부작용/리스크 | 다이어트/피부 관리 | 한국 의료 트렌드

### 아티클 구조
Hook → 핵심 정보 → 비교/선택 기준 → 리스크 → 결론 → CTA(고민 등록)

### 다국어
한국어 (primary, 정보성 톤) + 중국어 간체 (secondary, 샤오홍슈 톤)

### 발행
1~2개/일, 70% 정보성 / 30% 전환형
